# Refresh boundaries

`ingest::ingest_all` coordinates five domain operations:

1. Prepare/publish memory changes using the refresh-owned repository resolver.
2. Recover the stored ingestion checkpoint under the existing ingestion lease.
3. Observe sources and classify changes.
4. Parse with bounded backpressure and lazily prepare a writer when records or deletions exist.
5. Persist prepared analytics and publish the index/checkpoints.

## Ownership

- `repository.rs`: local-only gix discovery. A resolver belongs to one refresh; memory and analytics share it. No process-global repository cache or Git subprocesses.
- `ingest/discovery.rs`: filesystem/database observations and source-specific readiness. Transcript observations use one bounded operation-owned pool. OpenCode retains its failed/absent/ready distinctions and legacy fallback rules.
- `ingest/plan.rs`: pure file-change and refresh decisions. New, unchanged, appended, replaced, and parser-changed files are explicit cases. Refresh decisions distinguish unchanged, checkpoint-only, and index work.
- `ingest/execution.rs`: source parsing, record transforms, bounded delivery, and checkpoint assembly. Small workloads avoid unnecessary parser-pool dispatch.
- `ingest/publication.rs`: recovery operations and the writer. Staging is delayed until the first record or required deletion/vector work. Private staging cannot publish before the durable decision.
- `AnalyticsWriter::prepare`: resolves session facts and labels before SQL persistence. The returned prepared batch borrows the writer until commit, preventing interleaved accumulation. Deletions and inserts commit in one transaction.
- `MemoryStore::prepare_refresh`: produces a prepared snapshot while holding its write lock; publication is a separate operation.

The existing ingestion lease is retained across observation and execution. Checkpoints are loaded under that lease, so competing refreshes re-observe committed state. Read-only searches remain independent of the indexing writer. The [checkpoint storage contract](checkpoint-storage.md) defines sparse reads/deltas, migration, lifecycle locking, and recovery ordering.

## Per-file failures

A transcript or database session that fails to parse, by error or panic, is isolated instead of failing the refresh. The attempt that hit it publishes nothing and writes no publication intent; the refresh then reruns the same selection with the failing files deferred, so everything else publishes. A deferred file keeps its indexed records and its checkpoint: a parse failure is never a deletion, and the file is reparsed from its last good checkpoint once it reads again. Discovery also keeps the projections a deferred Claude agent owner would have retired, so merged agent copies stay all-or-nothing.

Failures are recorded in `state/ingest-failures.json` with source, path, error, first and last attempt, attempt count, and the observed identity. Discovery defers a recorded file until its retry time, which starts at 30 seconds and doubles per failed attempt up to an hour, or until its size, timestamps, inode, or prefix identity change. The watcher treats hints for a deferred file as no-ops on the same terms. A successful parse or deletion clears the entry, and a full scan drops entries for files it no longer sees. `memex stats` (text and JSON) and `memex daemon status` list the skipped files.

Tasks named by an interrupted publication intent and OpenCode sessions are not isolated: recovery must replay every path its intent names, and OpenCode sessions share database ownership, so their failure still fails the refresh.

## Cost contracts

- An unchanged refresh creates no lexical staging generation, writer, commit, or merge work.
- Full discovery for Claude, Codex, Pi, Omp, and Muse reuses directory stamps. Other providers retain their source-specific discovery. Each successful refresh records device, inode, and mtime for every directory the stamped walk enumerated, keyed by a fingerprint of the source roots, provider flags, and exclude patterns. The next full scan stats each stamped directory and reads only those whose stamp moved, taking the files of unchanged directories from the checkpoint. A directory's mtime changes on entry creation, removal, or rename and never on in-place appends, so known files keep their individual stat check. Stamps are written in the same checkpoint transaction as the file rows; a failed refresh persists none.
- Read-triggered refreshes on macOS replay the volume's persistent file-system event journal instead of walking. Every committed refresh stores the journal position it captured before reading anything, keyed by the discovery fingerprint plus the roots that existed. The next refresh replays events under the source roots from that position, unions them with the same sweep candidates the watch daemon stats — transcripts the checkpoint saw modified inside its hot window, plus every tracked database, whose writer can commit to the WAL for a whole session while the main file's mtime stays cold — and resolves the result exactly as the watch daemon resolves its dirty set: only those paths are stat-checked and parsed. FSEvents defers content-modification events for a file held open for writing, so that shared candidate set, not the event stream, is what bounds staleness for an active session. A directory rename or removal, a dropped or wrapped event range, a purged journal, a cursor more than 500,000 events behind (the event stream is host-wide, so activity on any volume counts toward that distance), a different volume, a root that started existing, a root that stopped being readable between the fingerprint and the replay, or a missing cursor leaves the journal unable to name the changes; explicit `memex index` runs always walk.
- A read replays the journal whatever the scan cache says; `index_freshness` decides what happens when the replay cannot name the changes. `strict` walks, `bounded` walks only once the last walk is older than `scan_cache_ttl` and otherwise reads the index as it stands, keeping the stored cursor so the unnamed interval is still covered later, and `none` skips read-time refreshes altogether.
- Session reads (`session_page`, `session_batch`, `read_session_pages`, `session`, over the CLI, MCP, the native socket, and RPC) refresh once per operation before reading. A read that names no source path is narrowed to every source the index holds for its session ID. Transcripts are stat'ed against their checkpoints and the ones whose size, identity, timestamps, or SQLite WAL moved are ingested, along with the store behind every database-backed session (Bob, ZCode, KiloCode, OpenCode), whose WAL-only commits leave its own metadata unchanged; a session that is still being written reads back its newest messages without waiting for the journal or the hot window. A source that cannot be narrowed this way — a legacy OpenCode session directory, a transcript that is gone, or a session the index does not hold yet — makes the read refresh as a search does. When the dirty selection cannot resolve a source on its own, the read walks only if `index_freshness` would walk for a search. Under `bounded`, a refresh that fails or waits more than a second for the lease leaves the read on the index as it stands with a warning; under `strict` it fails the read, and in a batch only the local pages report it.
- Searches follow the same rule: under `bounded` a search waits a second for an ingest that holds the lease, and a refresh that fails or cannot get the lease leaves the search on the index as it stands with a warning; under `strict` it waits up to 30 s and fails the search.
- Read-triggered refreshes (searches, session reads, TUI auto-index) spend at most 10 s embedding, checked between embedding batches. Records past that budget are published without vectors, and later refreshes, explicit `memex index`, or `memex index embed` backfill them, so a slow embedder or a large vector backlog cannot hold the lease for the length of the backlog. Explicit and daemon indexing are unbounded.
- The replay runs on its own thread, registered with fseventsd before the process writes its lease or opens the checkpoint, and overlaps checkpoint recovery and memory refresh. A write on the volume in the milliseconds before registration makes fseventsd hold the answer for about 160 ms; a replay not answered within 50 ms of starting is abandoned and the refresh walks. The captured cursor is persisted either way.
- A parsed update with no indexable records advances checkpoints without opening a lexical writer.
- Metadata enrichment performs no subprocess calls. SQL persistence performs no source or repository discovery.
- Source-ID presence checks reuse one reader; analytics inventory returns only candidate paths.
- Record delivery remains bounded. Parsed whole-corpus records are never accumulated in a vector.
- A refresh indexes with one worker per 8 MiB of new source bytes, up to tantivy's default of one per core and at most eight; a rebuild keeps its own writer below. Every worker that receives a record publishes its own segment, and on local transcripts one worker indexed up to 8 MiB as fast as eight did (1.4 MB: 40 ms against 58 ms; 6.3 MB: 69 ms against 68 ms), so a typical append publishes one segment, and two workers beat eight up to 16 MB. A refresh whose size is unknown, because legacy OpenCode session files do not reflect the message files they read, uses tantivy's default. No refresh merges in the foreground: explicit `memex index`, daemon indexing, and read-triggered refreshes (searches, session reads, TUI auto-index) all stage a continuous-ingest generation and append with `NoMergePolicy`, one segment per commit, and each of them schedules the detached compaction below once it has released the lease. `memex index rebuild` indexes into a 1 GiB arena across the indexing threads (at most eight) with no merges and publishes the segments as written, about one per thread while the corpus fits the arena. Each of those holds well over 5 % of the corpus, so the detached compaction leaves them as written; it folds a rebuild's segments only when a corpus that overflows the arena splits into segments under that share. Parse tasks start with the largest remaining input so one big transcript cannot become the tail of the parse phase, analytics receives each session's working directory from its parser instead of re-reading the transcript, and transcripts are mapped with `MADV_SEQUENTIAL` so a cold rebuild reads with a wide read-ahead window instead of the kernel's default fault-around. On a 200-file, 67k-record corpus the rebuild went from 14.7 s to 1.6 s and explicit indexing from 10.3 s to 1.6 s.
- When a refresh that added records leaves more than 8 small segments (under 5 % of the corpus, outside the three largest) it spawns one detached `memex index compact` process, which merges those small segments into one and exits. Segments at or above the 5 % share are left alone even when they fall outside the three largest. The spawn is skipped while any ingest holds the lease. A separate compaction lock stays held across the merge, so duplicate children exit without merging and at most one compaction runs at a time; no resident process is involved.
- The compaction holds the ingest lease only to stage from the current generation and to publish. When another refresh published while it merged, it discards its merge and leaves `state/compaction.pending`; explicit `memex index`, daemon ingests, and read-triggered refreshes then spawn it again on their next run whether or not that run added records, and a failed spawn leaves the same marker. Each retry starts from the newest generation and merges only the small segments, so it needs a gap between publications about as long as that merge; the event-driven daemon starts each ingest at least 5 s after the previous one finished. A continuous refresh that would publish more than 4096 segments is refused, which bounds the segments that can accumulate if compaction never publishes.
- Publication intent is written once after parsing has determined the final document-ID checkpoint and before shared record mutations. Existing pending recovery is retained on cancellation.
